# Feature Specification: 抓取任务增加登录态校验

## Overview

在价格监控和详情抓取任务执行每批次前，通过 AI 视觉理解检测浏览器登录状态。未登录时中止任务，避免在无登录态下继续抓取导致数据缺失或商品被误标记为失效。

## Problem Statement

当前抓取脚本（价格监控、详情抓取）在每批次执行前不校验浏览器登录态。如果上下文的登录态过期或丢失：
- 抓取会继续执行但获取到的是登录/验证页面而非商品数据
- 商品数据更新为空值，被误判为失效
- 浪费浏览器资源和时间
- 需要人工排查并修复被误标记的数据

## Goals

- 每批次执行前自动检测登录状态
- 未登录时立即中止任务并给出明确错误提示
- 登录态正常时，如果商品确实无法访问，恢复标记为失效的逻辑
- 覆盖两个抓取脚本：价格监控和详情抓取

## Non-Goals

- 不修改上下文管理或登录流程本身
- 不修改关键词搜索脚本（它们已有"关闭登录弹窗"的逻辑）
- 不实现自动重新登录（未登录时中止任务，由用户手动重新登录）

## User Scenarios & Testing

### Primary Scenario 1：登录态正常，正常抓取

1. 用户启动一批电商链接监控任务
2. 每批次开始前，系统自动导航到平台首页检测登录态
3. 检测到登录态正常
4. 正常执行抓取流程
5. 对于确实无法访问的商品（页面返回 404、商品下架等），标记为失效

### Primary Scenario 2：登录态失效，任务中止

1. 用户启动一批电商链接监控任务
2. 每批次开始前，系统检测登录态
3. 检测到未登录（页面出现登录表单或跳转到登录页）
4. 任务立即标记为失败，错误信息明确提示"登录态已失效，请重新登录"
5. 该批次剩余商品不被处理，不会被误标记

### Edge Cases

- 检测登录态时网络超时或页面加载失败：任务标记为失败，提示网络异常
- 检测结果不确定（AI 返回模糊结果）：视为未登录，中止任务
- 混合场景：批次中部分商品成功、部分失败——成功部分正常保存，失败部分仅在确认登录态正常后标记失效
- 平台差异：不同电商平台有不同的登录态表现（京东用户名区域、淘宝/天猫用户头像区域等）

## Functional Requirements

### FR-1: 每批次执行前校验登录态

**Description**: 在价格监控和详情抓取脚本中，每批次开始处理商品 URL 之前，先检测当前浏览器的登录状态。

**Acceptance Criteria**:
- 校验发生在批次循环体内部、处理商品 URL 列表之前
- 校验通过后才开始处理该批次的商品
- 校验不通过时，该批次中止，任务标记为失败
- 错误信息包含平台名称和明确的"登录态已失效"提示
- 校验结果记录到任务日志中

### FR-2: 登录态检测方式

**Description**: 使用 AI 视觉理解（agent.extract）判断页面是否处于已登录状态。

**Acceptance Criteria**:
- 先导航到平台首页（如 `https://www.jd.com`、`https://www.taobao.com`），再检测登录态
- 使用结构化提取，返回明确的"已登录"/"未登录"结果
- 检测逻辑对每个平台分别处理（因为登录态的页面表现不同）
- 检测超时（默认 30 秒）视为未登录

### FR-3: 未登录时的处理

**Description**: 检测到未登录时，中止当前任务。

**Acceptance Criteria**:
- 任务状态改为"失败"
- 错误信息为"登录态已失效，请重新登录 [平台名称]"
- 当前批次未处理的商品不改变状态（保持原有 monitor_status）
- 已处理的商品结果正常保存

### FR-4: 恢复商品失效标记

**Description**: 在确认登录态正常的前提下，如果抓取过程中发现商品确实无法访问（页面 404、商品下架、链接失效），将其标记为失效状态。

**Acceptance Criteria**:
- 仅在登录态校验通过后才进行失效标记
- 判断条件：页面明确无法提供商品数据（非登录拦截导致的空数据）
- 标记为失效时同步记录原因（如"商品下架"、"页面 404"等）
- 瞬时错误（网络超时、页面加载失败）不标记为失效，仅记录错误日志

## Success Criteria

- 登录态失效时任务被中止，不会继续处理商品
- 任务日志中明确记录登录态检测结果
- 登录态正常时，真正失效的商品被正确标记
- 登录态失效时，没有任何商品被误标记为失效
- 覆盖价格监控和详情抓取两种任务类型

## Key Entities

| Entity                   | Description                                                    |
|--------------------------|----------------------------------------------------------------|
| 登录态检测结果            | 结构化数据，包含平台名称、是否已登录、检测时间                   |
| 商品失效状态              | 商品链接的 monitor_status 变更为 invalid，附带失效原因           |
| 任务日志                 | 记录登录态检测步骤和结果                                        |

## Assumptions

- 各平台首页是检测登录态的可靠入口（京东 `jd.com`、淘宝 `taobao.com` 等）
- AI 视觉理解能可靠区分"已登录"和"未登录"状态
- 如果批次执行中途登录态丢失（极少见），当前批次已处理部分的结果仍可信任
- 失效标记的条件：页面明确返回下架/404 信息，而不是单纯的数据为空（数据为空可能是页面结构变化，不一定是失效）

## Dependencies

- AgentBay SDK 的 `agent.extract` 方法可用且稳定
- 各平台首页在未登录状态下有明确的登录入口特征
- 任务日志系统支持记录新增的登录态检测步骤

## Open Questions

无（用户已明确使用 agent.extract 方案，检测位置和错误处理方式已确认）
